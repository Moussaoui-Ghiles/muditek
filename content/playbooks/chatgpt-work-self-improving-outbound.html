Build a Self-Improving Outbound System With ChatGPT Work

Turn each week of outbound outcomes into one tested change to account scoring or message instructions.

The outbound system runs the work. This review system improves the rules behind that work. It cannot send, scrape people, approve its own change, or put anything live.

Everything starts offline. GPT reads plain files, proposes one edit, tests it on known cases, and prepares a review page. You decide whether the change becomes part of the next outbound run.

The two-system model

Do not give the review system access to delivery.

System 1 runs outbound

It senses the market, scores the account, writes from the buying signal, checks the message, records the outcome, and learns from the reply.

System 2 improves System 1

It reads saved outcomes, proposes one scoring or message change, tests that change, and prepares it for your approval.

Keep System 2 offline until the files and tests work. Do not connect a CRM, enrichment provider, or sending tool. The first job is to prove that GPT can make one controlled improvement without touching a real prospect.

Sending and approval stay outside the loop. GPT proposes. You decide what becomes live.

Create the project files

GPT can only improve decisions it can read.

The setup uses plain files. One file sets the limits. One holds company scoring. One holds message rules. One stores outcomes. A fixed test set checks whether a proposed scoring change helped.

1. Set the operating limits

Define what GPT may do before you give it anything to edit.

The limits must be short enough to inspect. GPT may change one scoring weight or one message instruction. It must cite the outcome rows behind the proposal. It must run the correct test and stop when the result does not improve.

AGENTS.md

# Self-Improving Outbound Rules

You improve an outbound system from outcomes.

Hard rules:
- Never send messages.
- Never scrape or enrich real people.
- Never self-merge.
- Edit only files in this repo.
- Change one concept at a time.
- Cite outcomes from memory/outcomes.jsonl for every proposed change.
- Improve evals/score.py before a change can become a PR.
- If the eval does not improve, revert your edit and stop.

Allowed edits:
- config/scoring.yaml
- config/plays.yaml
- prompts/*.md

Required output:
- changed files
- reason for each change
- before score
- after score
- pull request summary

The output of this step is a hard boundary: read outcomes, propose one file change, prove it helped, and wait.

2. Put company scoring in one file

A model cannot improve qualification logic that only lives in someone’s head.

Each buying signal receives a weight. Negative signals receive a penalty. Add the weights to produce the company score. Two score limits route the account to ignore, draft, or human review.

config/scoring.yaml

signals:
  competitor_comparison:
    weight: 8
    reason: "buyer is comparing alternatives"
  implementation_page_visit:
    weight: 6
    reason: "buyer is checking whether this can be installed"
  job_repost:
    weight: 5
    reason: "role is still open and urgent"
  funding_event:
    weight: 5
    reason: "budget or mandate may have changed"
  generic_download:
    weight: 1
    reason: "content interest, weak buying intent"

thresholds:
  draft: 6
  human_review: 10

negative_signals:
  student_research: -8
  vendor_pitch: -6
  competitor: -10
Total company scoreAction
Below 6Ignore the account.
6 to 9Prepare a message draft.
10 or moreSend the account for human review.

Keep the first version small. The file is a visible business hypothesis, not a permanent truth. A reviewer must be able to point to one line and explain why it should change.

Do not add a new exception for every unusual account. Too many weights and special cases will make the system fit old examples instead of future buyers.

3. Record every outcome with a reason

A reply label tells you what happened. The reason tells you what to change.

Write one row when the outcome becomes known. Save the account, signal, message play, company score, outcome, and reason. Do not fill the file from memory at the end of the week.

memory/outcomes.jsonl

{"date":"2026-07-01","account":"Northwind Finance","signal":"competitor_comparison","play":"migration_note","score":8,"outcome":"reply","reason":"asked for migration notes"}
{"date":"2026-07-01","account":"Bluepeak Studio","signal":"generic_download","play":"resource_followup","score":1,"outcome":"no_reply","reason":"content-only intent"}
{"date":"2026-07-02","account":"KiteOps","signal":"implementation_page_visit","play":"implementation_angle","score":6,"outcome":"reply","reason":"asked about implementation timeline"}
{"date":"2026-07-02","account":"Atlas Recruiting","signal":"job_repost","play":"hiring_angle","score":5,"outcome":"bad_fit","reason":"student research request"}

no_reply alone says little. content-only intent explains why a generic download may not deserve a message draft. bad_fit becomes useful only when the reason explains the mismatch.

Validate every outcome before saving it

4. Build the scoring test

A proposed score change must beat a fixed set of known decisions.

Create a small test set with strong signals, weak intent, bad fits, and accounts the current scoring routes incorrectly. For every account, record the expected action before GPT proposes a change.

evals/fixtures.yaml

cases:
  - account: Northwind Finance
    signals: [competitor_comparison, implementation_page_visit]
    expected: human_review
    note: "two strong signals on one account"

  - account: Bluepeak Studio
    signals: [generic_download]
    expected: ignore
    note: "content-only intent"

  - account: KiteOps
    signals: [implementation_page_visit]
    expected: draft
    note: "implementation intent should clear draft threshold"

  - account: Atlas Recruiting
    signals: [job_repost, student_research]
    expected: ignore
    note: "bad-fit marker cancels the signal"

Build evals/score.py

Build evals/score.py.

Read config/scoring.yaml and evals/fixtures.yaml.

For each case:
1. Sum weights for every signal.
2. Add negative signal penalties.
3. Route the account:
   - score >= thresholds.human_review => human_review
   - score >= thresholds.draft => draft
   - otherwise => ignore
4. Compare route to expected.

Print each prediction.
Print final accuracy as score=0.00 to score=1.00.
Exit 0 only when accuracy is 1.00.

Baseline result

Northwind Finance: predicted=human_review expected=human_review
Bluepeak Studio: predicted=ignore expected=ignore
KiteOps: predicted=ignore expected=draft
Atlas Recruiting: predicted=ignore expected=ignore
score=0.75

The baseline makes three correct decisions out of four. It routes KiteOps to ignore even though the expected action is draft. That known miss becomes the problem a useful score change must fix.

Do not fill the test set with obvious wins. A weak test will approve a bad change.

5. Test one signal weight

Change one number, for one reason, and run the same test again.

GPT reads the operating limits, scoring file, outcome log, and fixed test cases. It may change only one signal weight. It must cite the exact outcome rows that support the proposal.

6. Improve message instructions separately

Do not change company scoring and message instructions in the same proposal.

A score change answers, “Which accounts should move?” A message change answers, “What should we say when they do?” Keeping the reviews separate makes the cause of any improvement clear.

config/plays.yaml

plays:
  migration_note:
    prompt_file: prompts/plays/migration_note.md
    use_when:
      - competitor_comparison
    banned_lines:
      - "thought this might be relevant"
      - "quick question"

  implementation_angle:
    prompt_file: prompts/plays/implementation_angle.md
    use_when:
      - implementation_page_visit
    banned_lines:
      - "checking out our solution"
      - "would love to chat"

prompts/improve_prompt.md

You improve one outbound play.

Read:
- AGENTS.md
- config/plays.yaml
- memory/outcomes.jsonl
- the prompt file for the chosen play

Pick one play with at least 10 outcomes.

Find:
- lines or structures that appear in positive outcomes
- lines or structures that appear in no_reply or bad_fit outcomes
- any phrase that should be banned

Make one small edit to that play's prompt.

Rules:
- Do not change scoring.
- Do not create a new play.
- Do not add a new channel.
- Cite outcome rows.
- Write the before and after instruction.

Then run the copy eval if present.
If no copy eval exists, open the PR as review_required.

A message play needs at least 10 outcomes before this review starts. GPT compares lines and structures from positive outcomes with those found in no replies and bad-fit outcomes. It proposes one small instruction change.

If there is no test for message quality, the proposal must say review_required. It cannot claim the new message is proven.

7. Review every proposal before it becomes live

GPT prepares the evidence. You make the decision.

Every proposed change arrives as a pull request. This is a review page that shows the exact edit, the outcome evidence, accuracy before and after, the risk, and what the reviewer should check.

prompts/pr_summary.md

Write a pull request summary for this outbound improvement.

Include:
1. What changed.
2. Why it changed, citing outcome rows.
3. Before score.
4. After score.
5. Files changed.
6. Risk.
7. What the human reviewer should check.

Keep it short.
Do not claim the change is live.

8. Run one review each week

Let outcomes collect before you change the system.

Do not run the review after every reply. One loud account can push the system toward a bad exception. Collect a full week of outcomes, then create one small proposal.

scripts/weekly_tune.sh

#!/usr/bin/env bash
set -euo pipefail

cd "$(dirname "$0")/.."

python3 evals/score.py || true
scripts/run_codex_step.sh improve_scoring
python3 evals/score.py
scripts/run_codex_step.sh pr_summary > outputs/pr-summary.md
scripts/open_pr.sh

Run every Monday at 08:00

Before you replace the sample data

  • The operating limits prevent sending, scraping real people, and self-approval.
  • The scoring file contains only the signals and score limits you can explain.
  • Every outcome row has a real reason, not only a reply label.
  • The fixed test includes weak intent, stale signals, bad fits, and known misses.
  • A scoring proposal changes only one signal weight.
  • A message proposal changes only one message instruction.
  • A failed test restores the previous file.
  • Every accepted proposal still waits for your approval.

After the offline version works, replace the sample outcomes with your own results, rename the buying signals, add your message plays, and build test cases from accounts you wish the system had routed differently.

The finished system produces one small, evidence-backed proposal. It never sends outreach or changes live outbound rules by itself.
