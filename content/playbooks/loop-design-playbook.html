What a Loop Actually Is

A loop is cron plus a decision-maker plus feedback.

Cron wakes something up.

The model reads the current state and decides what action to take.

Tools execute that action.

A verifier checks the result.

The loop either keeps going, hands off, or stops.

The important shift is role reversal. You stop being the person inside the loop typing the next prompt. You become the person who writes the loop, owns the constraints, and decides what work deserves to run without you.

That is why the phrase matters. Not because prompt engineering disappeared. It moved into a smaller, harder artifact: the loop spec.

The Five-Level Ladder

The word "loop" gets messy because people use it for five different things. Put them in order and the fight gets clearer.

Level 1

ReAct Loop

One model reasons, calls a tool, reads the result, and repeats. Useful, but usually watched by a human.

Level 2

Goal Loop

The agent keeps prompting itself toward a goal. Powerful when bounded, useless when it spins.

Level 3

Ralph Loop

A fixed prompt and fixed context get rerun until the work converges. The discipline is context reset.

Level 4

Validator Loop

The agent keeps working until a separate validator says the task is done. This is where trust starts.

Level 5

Orchestration Loop

One loop schedules, dispatches, supervises, and recovers other loops. The unit of work becomes the loop itself.

Most people arguing online are mixing Level 2 and Level 5. The new part is not "run the same prompt again." The new part is durable orchestration: scheduled work, multiple agents, shared state, crash recovery, and verification that survives your laptop closing.

The Production Blueprint

A production loop has six parts. If one is missing, the system is incomplete.

TriggerWhen the loop wakes up: cron, webhook, pull request, Slack message, file change.The human has to remember to start it.
StateWhat the loop knows between runs: repo, issues, memory files, queue, decision log.Every run starts from amnesia.
WorkerThe agent that decides and acts. Claude Code, OpenClaw, Hermes Agent, Codex, or another operator.The loop cannot choose the next move.

The model is one cell in the table. The expensive engineering is everything around it.

Skills as Repeatable Procedures

The loop is plumbing. The asset is the skill it calls.

A prompt tells an agent what you want this time. A skill teaches the agent how your business does a repeatable job every time.

If the loop has no skill library, it has to rediscover your standards on every run: how you review a pull request, how you qualify a lead, how you write a CTA, how you decide whether a claim is safe.

Without a stable procedure, output quality changes between runs and becomes harder to audit.

Loop design compounds only when the loop calls named skills with narrow ownership, explicit inputs, expected outputs, and refusal conditions.

In a business system, this maps to three inputs: business context, procedures, and approved data sources. The loop reads the context. The skill performs the job. The verifier checks the result.

Build the Smallest Useful Loop

Do not start with a broad company-wide workflow. Start with one bounded recurring process.

The canonical starter is pull-request babysitting: watch open PRs, fix build failures, address comments, rerun checks, and stop when the PR is clean or blocked.

It works because the state is concrete, the tools are available, the verifier is obvious, and the blast radius is bounded.

Starter Loop Command

/loop babysit all my PRs.
Auto-fix build issues.
When review comments come in, use a worktree agent to fix them.
Rerun checks after every fix.
Stop when every PR is green, blocked on human input, or has hit the budget ceiling.

That command is not the system. It is the top layer. The system is the contract below it.

Guardrails That Keep It Alive

A loop that almost works can continue for too long without a clear failure signal.

Every serious loop needs three hard stops before it touches live work.

  • Iteration ceiling. Decide how many passes it gets before escalation.
  • No-progress detection. If two consecutive runs change nothing important, stop.
  • Spend ceiling. Cap tokens, dollars, API credits, or runtime before the loop starts.

Then add the fourth guardrail: permission boundaries. The loop can read broadly, but it should write narrowly. If it needs to cross a boundary, it asks.

A loop without a verifier cannot establish that the work is correct. A loop without a halt condition cannot bound cost or failure. A loop without stable procedures produces inconsistent work.

The First Week Rollout

A good first loop is bounded and observable.

You are proving the control system, not chasing the most impressive demo.

DayBuildExit Condition
Day 1Pick one recurring surface. Write the loop spec. Name the state, tools, verifier, and stop rules.A human can read the spec and know exactly what the loop may touch.
Day 2Create two skills: the worker skill and the verification skill.The agent has a named procedure instead of a vague instruction.
Day 3Run manually once with full observation.You catch missing permissions, missing context, and vague done criteria.
Day 4Add budget, iteration, and no-progress stops.The loop cannot run forever.
Day 5Schedule it. Keep the first schedule conservative.The loop runs without you starting it.
Day 6Write every mistake into memory or the skill file.The second run is cleaner than the first.
Day 7Promote or kill it.If it saved attention and did not create hidden risk, expand the scope. If not, tighten or delete.

The win is not that the agent did work. The win is that the same work can run again with better context, better stops, and a cleaner verifier.

The Honest Limits

Loops do not remove judgment. They move judgment earlier.

You still decide which workflows deserve automation. You still define the blast radius. You still own the verifier. You still kill the loop when the economics stop making sense.

  • Do not loop weak work. If the workflow is unclear manually, automation makes the confusion run faster.
  • Do not let the worker grade itself. Use tests, logs, screenshots, reviewer models, or human approval where risk matters.
  • Do not hide cost. Make spend visible per loop, not buried in one account-level model bill.
  • Do not confuse agents with systems. A powerful model inside a weak loop is still a weak system.

The practical answer to "WTF is a loop?" is simple.

It is the system that lets an agent work when you are not watching, without pretending the agent is safe by default.

Write the loop. Give it skills. Force verification. Cap the downside. Then let it run.
